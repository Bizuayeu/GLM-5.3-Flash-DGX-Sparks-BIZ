# Host preparation

[日本語](hosts.ja.md) · [Repository README](../README.md) · [Host tools](../host/README.md)

What every serving line needs from its hosts before the line's own setup: the kernel and driver to run, the GPU clock cap, and the host's own users of memory and a peer that stops answering. Cabling and the fabric are in [QSFP network](qsfp-network.md) and [NCCL diagnostics](nccl-validation.md); each line's runbook ([1.x](../v1/SETUP.md), [2.x](../v2/SETUP.md)) or, for 3.x, its [README](../v3/README.md#requirements) links here.

## Host kernel and multi-node RoCE

**Check the kernel and the driver before installing updates and before the multi-host steps.** The reference hosts, MSI EdgeXpert (MS-C931), run DGX OS 7.6.0. Since 2026-11-07 they boot kernel `7.0.0-1025-nvidia` with `kho=off` and `power_wrap_init` in `initcall_blacklist`, with driver 580.178.04, ConnectX-7 firmware 28.50.1002 and MSI's UEFI 5.36_1.9.0 with the display memory set to Auto ([updating a host](#updating-a-host)). No figure of any line has been measured on this state yet. From 2026-10-14 to 2026-11-07 they booted `7.0.0-1019-nvidia` with `kho=off`, with the same driver, ConnectX-7 firmware 28.45.4028, MSI's earlier board firmware (EC 10800, SoC 10900, USB-C PD 522) and the display memory at its 2 GiB default, which left `MemTotal` 1.5 GiB lower. 2.9.1 and 2.9.2 were accepted on that state, and every 3.x release through 3.11.4 was measured there. Earlier measurements, 1.x's through 1.31.0 and 2.x's through 2.9.0, ran on `6.17.0-1032-nvidia` with driver 580.173.02 and ConnectX-7 firmware 28.45.4028.

Updates available as of 2026-09-15 move the `linux-nvidia-hwe-24.04` metapackages to `7.0.0-1019-nvidia`, with the 580 open driver modules built for it. The same update moves `nvidia-driver-580-open` from 580.173.02 to 580.178.04 (seen in `apt list --upgradable` on both reference hosts, 2026-09-18). An `apt` upgrade or a DGX Dashboard update installs it, so a newly installed system boots it after its first update.

With that kernel's defaults, two-host NCCL over RoCE can fail with `NCCL WARN Call to ibv_reg_mr_iova2 failed with error Cannot allocate memory`. Reports describe the model loading and then failing during vLLM profiling or tensor-parallel communication, while raw RDMA tests such as `ib_write_bw` look healthy. NVIDIA's [update advisory](https://forums.developer.nvidia.com/t/dgx-spark-update-advisory/383254) (2026-09-13) recommends that multi-node/RoCE users hold off on this kernel, including updates through DGX Dashboard, and names no fixed release. Whether single-host workloads are affected is not established.

The analysis in [NV-Kernels PR #590](https://github.com/NVIDIA/NV-Kernels/pull/590) (open; a contributor's analysis, not an NVIDIA statement) traces the failure to Kexec HandOver (KHO). The `7.0.0-1019-nvidia` build sets `CONFIG_KEXEC_HANDOVER_ENABLE_DEFAULT=y` (checked in its package config; `6.17.0-1032-nvidia` does not enable KHO by default). At boot, KHO reserves scratch memory for a later kexec and releases it as CMA pageblocks, about 9.3 GiB (4,761 pageblocks) in that report, without counting them in `CmaTotal`. RDMA memory registration pins pages long-term, and pinned pages must first move out of CMA; under GPU memory pressure that migration fails and registration returns `ENOMEM`.

Boot every host with KHO off, as the reference hosts do:

1. With the update installed, `sudo apt install nvidia-spark-grub-kho`. NVIDIA's package adds `/etc/default/grub.d/nvidia-spark-kho.cfg`, which appends `kho=off` to `GRUB_CMDLINE_LINUX_DEFAULT`; the reference hosts took it. Without the package, add `kho=off` to `GRUB_CMDLINE_LINUX_DEFAULT` in `/etc/default/grub` yourself, keeping the existing values.
2. `sudo update-grub` if you edited the file by hand, then reboot.
3. Confirm `kho=off` in `/proc/cmdline`; `sudo ls /sys/kernel/debug/kho` must fail with "No such file or directory".

KHO serves kexec-based live update, which this deployment does not use. The workaround was posted in the advisory thread, and the PR reports two-host registration, NCCL and TP2 workload tests passing with KHO off. `kho=off` does nothing for the host freeze described below.

On the 2026-10-14 state the reference hosts passed, against the same work on `6.17.0-1032-nvidia` and 580.173.02 before the update:

- The [NCCL validation](nccl-validation.md) between the pair and around the three-host ring (2026-10-14).
- 1.x's vLLM at TP=2 (2026-10-15): with MTP, prompts of 1,024 to 32,768 tokens filled in 0.93 to 1.00 of the earlier times and decode ran at 33.93 and 24.97 tok/s against 33.45 and 24.42; without MTP, 14.16 and 14.18 tok/s against 14.09 and 14.09.
- A night of serving tests on TensorFold's native engine at TP=2 and TP=3 (2026-10-14 to 15): 46 timings, each within 3% of the same test on the earlier kernel.
- 2.9.1's acceptance window (2026-10-15), with 2.9.0's token ids, replies, NLL and tool-eval scores ([2.x changelog](../v2/CHANGELOG.md)). It ran on a warm afternoon: during tool-eval-bench's seven-minute runs at TP=2 the hottest ACPI zone read up to 95.0 °C, at or above 94 °C twice on each host and never twice in a row, so the [thermal watch](../host/README.md#during-long-runs) (two readings in a row at 94 °C or above) left the engine running. 2.9.0's window, at 05:00, peaked at 92.1 °C.

**The same update carries a report of a second failure, unrelated to RoCE.** Another two-Spark recipe reports both hosts freezing under ordinary serving load within about 24 hours of the DGX OS 7.5.0 → 7.6.0 update (kernel `7.0.0-1019-nvidia`, driver 580.178.04, Docker 29.6.2) (amasu, forum-post draft in commit `030d37e`; no code adopted). Over two days and two serving stacks it happened five or more times: ping still answered, sshd did not, and only a power cycle recovered the host. The kernel log before each freeze shows bursts of `NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY] ... returned from _memdescAlloc` (65 and 148 in one boot), with MemAvailable at 9.4 GB and about 73% of swap free, and no OOM-killer event, Xid or panic. The same hosts are described as stable for weeks on 7.5.0 with 580.173.02. The report also notes that the 7.6.0 release notes name 580.173.02 as the Spark driver and that the 580.178.04 support matrix does not list GB10. It is a draft whose hardware-diagnostic results are not filled in; what it shows is correlation, not an established cause. KHO explains the failed RDMA registration and does not explain this freeze. The reference hosts have run 7.6.0 with 580.178.04 since 2026-10-14 under the work above, serving tests through the night among it, without a freeze. Their kernel logged no such line until 2.9.1's window, where one host logged three while the model loaded and its memory was nearly full, and served on; on `6.17.0-1032-nvidia` with 580.173.02 the same hosts had logged 797 and 1,448 in a boot without freezing. The lines come with memory pressure, so compare a host's count with its usual one rather than with zero. If the symptom appears after an update, check the previous boot with `journalctl -b -1 -k | grep -c _memdescAlloc`.

After the update, repeat the [NCCL validation](nccl-validation.md) and a full-model launch before serving.

A separate report with the same error, on MS-C931 systems running an Ubuntu generic 7.0 kernel with driver 595.84, failed with about 118 GiB free before weights loaded and attributes the fix to MSI board firmware updates (embedded controller, SoC firmware, USB-C PD) ([MiaAI-Lab issue #259](https://github.com/MiaAI-Lab/DeepSeek-v4-Flash-DSpark-2x-DGX-Spark/issues/259)). If the error appears without memory pressure, check the vendor firmware as well.

**Check loaded clocks after an unclean restart.** tonyd2wild reports a persistent ~14 W clamp after watchdog resets: 611–890 MHz under load, with BF16 matrix throughput about half the unaffected host. GPU reset, clock/power settings and reboots did not restore it; disconnecting and reconnecting AC did. Running CUDA immediately after a GPU reset without a reboot also faulted (speed-night report, commit `9f5cc2c`; no code adopted). This is an external observation, not reproduced on this reference pair. Before attributing a post-restart slowdown to a model change, record GPU clocks and power under the same workload; an idle power reading alone does not diagnose the clamp.

## Updating a host

On 2026-11-07 the reference hosts moved from the 2026-10-14 state to `7.0.0-1025-nvidia`. These are the steps they took, in order, each with the check that showed it held.

1. **Packages.** `sudo apt update && sudo apt full-upgrade`, and `sudo apt install nvidia-spark-grub-kho` where it is not installed yet. NVIDIA ships the boot settings new kernels need as `nvidia-spark-*` packages, so update the package lists before the kernel comes in. Run the upgrade from the console or detached from your SSH session: unpacking `openssh-server` stops sshd for a moment, and a session that drops in the middle leaves packages unconfigured until `sudo dpkg --configure -a`.
2. **The ConnectX-7 firmware, before the reboot.** DGX OS 7.6's `nvidia-spark-mlnx-firmware-manager` (6.0.1-1) writes ConnectX-7 firmware 28.50.1002 from its package script, about two minutes (104 s on one reference host), and checks it on the next boot. Reboot only when `systemctl is-active nvidia-spark-mlnx-firmware-manager.service` no longer reads `active`. A reboot during the write stops it, and after three stopped attempts the unit logs `Install and verify exceeded retry limit (3)`, disables itself and leaves the old firmware running: so it went on two reference hosts, whose links kept working on 28.45.4028 while `systemctl is-system-running` read `degraded`. To write it again, `sudo systemctl reset-failed nvidia-spark-mlnx-firmware-manager.service && sudo systemctl enable --now nvidia-spark-mlnx-firmware-manager.service`, wait for `Please reboot the system` in `journalctl -u nvidia-spark-mlnx-firmware-manager`, and reboot; the next boot verifies the write and disables the unit. `cat /sys/class/infiniband/*/fw_ver` shows the running version.
3. **The boot settings.** After the reboot `/proc/cmdline` holds `kho=off` and `initcall_blacklist=tegra234_cbb_init,power_wrap_init`. `nvidia-spark-initcall-bl` 1.0-2 (2026-11-03) adds `power_wrap_init`; it answers reports of hosts rebooting again and again on `7.0.0-1024-nvidia` ([NVIDIA forum](https://forums.developer.nvidia.com/t/dgx-spark-repeatedly-rebooting-after-most-recent-update/387397)). The reference hosts never ran 1024: they went to 1025 with 1.0-2 already installed.
4. **Board firmware and display memory (MSI MS-C931).** The reference hosts then took MSI's board firmware from LVFS's `lvfs-testing` remote, which fwupd leaves disabled by default: `sudo fwupdmgr enable-remote lvfs-testing`, `sudo fwupdmgr refresh --force`, `sudo fwupdmgr update`, and a reboot, repeated until nothing is offered (EC 11000, SoC 11100 with UEFI 5.36_1.9.0, USB-C PD 525; a capsule reboot took about 7.5 minutes, and on one host the PD needed a second round). It is testing-channel firmware, taken here for the display memory setting; whether to take it is your choice, and other GB10 systems have their own firmware. With that UEFI the memory it reserves for a display can be set to Auto (Advanced → Advanced Menu → Display Reserved Memory, or from Linux with the request variable below). On a host that boots without a display (`multi-user.target`), Auto reserves 512 MiB instead of 2 GiB, and `MemTotal` rose by 1.50 GiB on every reference host, from 127,598,812 kB to 129,168,464 kB on one ([NVIDIA's porting guide](https://docs.nvidia.com/dgx/dgx-spark-porting-guide/latest/optimization.html) describes the setting). Every figure of every line was measured with the 2 GiB default.

   ```sh
   V=/sys/firmware/efi/efivars; G=284e19b9-235f-4aab-ae4c-190456d1bd76
   sudo od -An -tx1 $V/NvidiaDispFrmStatus-$G    # missing: this firmware has no Auto
   sudo chattr -i $V/NvidiaDispFrmSizeRequest-$G 2>/dev/null
   printf '\x07\x00\x00\x00\x00' | sudo tee $V/NvidiaDispFrmSizeRequest-$G > /dev/null
   sudo reboot
   ```

   After the reboot `NvidiaDispFrmStatus` reads `06 00 00 00 00 00 02 00 00`: four bytes of attributes, the setting (`00` is Auto), and the size in MiB, little-endian (`02 00 00` here, 512 MiB). The UEFI applies the request and removes it; firmware without Auto drops it silently.
5. **NCCL.** Repeat the [NCCL validation](nccl-validation.md). On `7.0.0-1025-nvidia` with ConnectX-7 28.50.1002 the reference hosts passed it between four directly cabled pairs (2026-11-07): 11 of 11 checks on both ranks, every channel over `NET/IB`, no `Cannot allocate memory`, and a 256 MiB FP32 AllReduce in 20.0 to 24.2 ms (24.6 ms for one of the pairs on `7.0.0-1019-nvidia`, 2026-10-11). The three-host ring and a full-model launch have not been repeated on this state.

## GPU clock cap

GB10 machines (DGX Spark and compatibles) are widely reported to power off under sustained GPU load, leaving no log and staying off until the power button is pressed. The reference pair's head did so once, on 2026-09-27, on the second of two back-to-back 261,573-token prefills after about 54 minutes of long-input load. Accumulated heat and the power peak of prefill are the likely causes; with no temperature or power record from that moment, this is not certain.

The mitigation that works in those reports is capping the GPU clock at 2,200 MHz instead of the default of about 2,418 MHz (`nvidia-smi -lgc 300,2200`; a power limit through `-pl` has no effect on GB10). The reference pair and its neighbor apply it at every boot and record temperatures, power and clock every two seconds. **1.x's [headline measurements](../v1/README.md#what-has-been-verified) were taken under this cap, and so was every 2.x and 3.x figure.** What the cap cost on 1.x against the same profile without it, in prefill, long inputs, decode, NLL, completions and correctness, is in [measurements](../v1/docs/benchmarks.md#both-profiles-in-one-window-with-a-gpu-clock-cap-2026-09-28). The cap is a host setting that no line's launcher applies; the [host tools](../host/README.md) install it as a boot unit, beside the telemetry logger. Benchmarks that send long requests one after another should rest between them.

## Swap, host daemons and a lost peer

On GB10 the GPU shares the host's memory, so the host's own state reaches the model. These were met or measured under 1.x and concern every line; each line's operations page says how its own guard acts.

### Swap

The reference hosts keep 16 GiB of swap for host pages. `vm.swappiness=0` stops new page-outs but leaves pages that are already swapped where they are, and touching old swapped pages during a long prefill was reported as the trigger of a GB10 UVM livelock (tonyd2wild's GB10 memory notes, no code adopted). Cycle residual swap while every container of the launch is down: `sudo swapoff -a && sudo swapon -a`. Keep the swap file itself; with no swap at all the worker was killed on allocation spikes. On 2026-09-17 the reference pair compared `vm.swappiness` 60 and 0 under 1.x at chunk 2048, cycling swap before the 0 arm. At 60 no engine process had swapped pages; 0.38 GiB on the head and 0.28 GiB on the peer belonged to other processes, such as a search container and the desktop shell. At 0 swap stayed empty, prefill differed by 1.9%, within the variation between restarts, and the head's lowest free memory was 0.45 GiB lower while the peer's was 0.31 GiB higher. No benefit showed for this workload, so the hosts stay at the distribution's 60. Another two-Spark recipe requires 0 persisted in `/etc/sysctl.d` (tonyd2wild OPEN-PROBLEMS §4, no code adopted); measure on your own load before persisting it.

### Host daemons

**Host daemons compete for the same unified memory.** Each line's memory guard stops the model when `MemAvailable` falls below its threshold (1.x's supervisor at its reserve, 2.x's and 3.x's `hostwatch.sh` at 5 GiB), but the cause can be another process on the host, and then the model stops while the cause remains. On 2026-09-16, under 1.x, the peer rank stopped at 2.49 GiB against a 2.5 GiB reserve. The cause was a monitoring dashboard on the other host that opened a new SSH login to the peer for every metric it sampled, 3.6 logins per second. Each login created a logind session and a polkit check, so `polkitd` grew to 3.40 GiB over six days; each session change made `wireplumber` re-register its Bluetooth audio profiles, which `bluetoothd` rejected as already registered, so both of those grew too (to 0.69 and 1.15 GiB); and each login ran every `/etc/update-motd.d` script, about 660 new processes per second. The host running the dashboard reads its own metrics locally and stayed at 0.03 GiB. Enabling OpenSSH connection reuse for the dashboard's host aliases (`ControlMaster auto`, `ControlPersist`) took the peer from 218 logins a minute to none, with the dashboard's readings unchanged. Before a long run, count logins on each host with `journalctl -u ssh --since -60s | grep -c Accepted` and compare daemon sizes with `ps -eo user,rss,comm --sort=-rss | head`. A `MemoryMax` drop-in on a daemon that leaks also needs `Restart=on-failure`, because these units ship `Restart=no` and would otherwise stay dead once the cap kills them. Finally, under 1.x a half-dead launch is invisible from the API: a surviving head keeps answering `/health` with 200, so check `docker ps` on every host.

**How the cause was found, and what held afterwards.** Counting new process and thread IDs separated the hosts (6,642 in 10 seconds on the peer against 176 on the head), and `journalctl -u ssh` traced the logins to the dashboard; Bluetooth was a symptom, not the cause. With connection reuse the peer's churn stopped, and after a power cycle the three daemons kept their size. The `polkitd` cap set during the incident (`MemoryMax=512M`, `Restart=on-failure`) stays on the peer as a second layer; its restart has not been exercised.

### A lost peer

**Under 1.x a lost peer is not detected while the launch is idle.** Mia issue #193 reports a head host that stopped answering on every network during sustained TP=2 serving and needed a physical reboot, with nothing logged before it; the worker kept running and held more than 100 GB until an operator stopped it. Two points carry over to 1.x. Each supervisor runs on the host it guards, so a host lockup takes its supervisor with it: the reserve guards against the model exhausting unified memory, not against the host locking up. And an idle half-dead launch is stopped by no supervisor: memory stays above the reserve, and stall detection needs a running request. A stop reason for a lost peer, with each rank checking the others, is a design note for 1.x and is not implemented.
